# ТЗ: Foundation + Rental Management MVP

## 1. Назначение проекта

Разработать **единый фундамент PropTech-платформы** для строительной компании с возможностью дальнейшего подключения отдельных модулей.
На текущем этапе реализуются только:

* **Foundation Core**
* **Rental Management**
* **Excel Import Center**

Система должна быть устроена так, чтобы сегодня данные загружались через Excel, а в будущем этот же фундамент можно было подключить к внешним API без перестройки доменной модели.

---

## 2. Что входит в текущий этап

### Входит

* компании и настройки компании;
* пользователи, роли, права доступа;
* реестр объектов;
* реестр контрагентов;
* реестр договоров;
* загрузка данных через Excel;
* документы и журнал действий;
* базовая система уведомлений внутри платформы;
* модуль аренды;
* API слоя для frontend и будущих интеграций.

### Не входит

* интеграция с Adesk как рабочий источник;
* управление строительством;
* cost management;
* маркетплейс стройматериалов;
* закупки;
* investor portal;
* массовые маркетинговые рассылки;
* сложная AI-аналитика.

---

## 3. Цель MVP

Сделать систему, в которой пользователь компании может:

1. создать свою компанию;
2. завести сотрудников и роли;
3. загрузить через Excel:

   * контрагентов,
   * объекты,
   * договоры;
4. вести учет объектов и собственников;
5. перевести объект в режим аренды;
6. вести арендаторов, договоры аренды, начисления, оплаты, депозиты, расходы;
7. получать отчет по объекту и собственнику.

---

## 4. Архитектурный принцип

Система должна быть **import-first, API-ready**.

Это означает:

* сейчас данные приходят через Excel;
* позже данные могут приходить через API;
* внутренняя доменная модель остается одной и той же.

Правильная цепочка:

**Excel / будущий API → Import/Integration Layer → Core Domain → Module Logic → REST API → UI**

Подход с `Company`, nullable `company_id`, новыми apps и feature flags уже ранее рассматривался как безопасное направление расширения, и его стоит сохранить в новой системе. 

---

## 5. Роли пользователей

### Системные роли

* **Super Admin** — владелец платформы;
* **Company Admin** — главный администратор конкретной компании.

### Рабочие роли компании

* **Sales / Client Manager** — работа с клиентами и договорами;
* **Finance / Accountant** — работа с оплатами, начислениями, отчетами;
* **Rental Manager** — ведение аренды;
* **Staff** — ограниченный доступ по назначенным разделам.

### Внешние роли

* **Owner / Client** — собственник объекта;
* **Tenant** — арендатор.

## 10. Технический стек

Для текущей разработки на Replit рекомендую:

* **Backend:** Django + Django REST Framework
* **DB:** PostgreSQL
* **Frontend:** React + TypeScript + Tailwind
* **Excel import:** Python `pandas` / `openpyxl`
* **Auth:** token auth / JWT
* **Storage:** local/S3-compatible abstraction
* **Background jobs:** Celery позже, сейчас можно sync + lightweight async tasks

Такой стек логично совпадает с тем, что уже использовалось в предыдущей архитектуре: Django 4.2 + DRF + PostgreSQL и React 18 + TypeScript + Tailwind.  

---

## 11. Ограничения и важные правила

* не делать лишние модули сейчас;
* не тащить стройку и закуп в MVP;
* не строить систему “только под Excel”;
* заложить future API-ready поля;
* не смешивать продажи и аренду в одну сущность;
* договоры продажи и договоры аренды должны различаться типом;
* весь новый функционал проектировать модульно;
* feature flags заложить сразу, даже если пока включены только foundation и rental. Ранее такой подход уже использовался для безопасного включения модулей. 

---

## 12. Критерии приемки

MVP считается готовым, если:

* можно создать компанию;
* можно создать роли и пользователей;
* можно импортировать контрагентов, объекты и договоры через Excel;
* можно открыть карточку объекта;
* можно назначить собственника объекту;
* можно включить объект в аренду;
* можно завести арендатора;
* можно создать договор аренды;
* можно начислить аренду;
* можно занести оплату;
* можно занести депозит;
* можно занести расход;
* можно увидеть задолженность;
* можно сформировать owner statement;
* все сущности имеют задел на будущую API-интеграцию.
